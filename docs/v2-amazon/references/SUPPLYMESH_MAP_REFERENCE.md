# SupplyMesh map reference for CargoMesh V2 — reviewed 24 September 2026

Status: **reference and data specification**, not a provider ADR, imported dependency, runtime integration or authorization to publish a deployment. Reviewed the [public demo](https://supplymesh-webmcp.vercel.app/) and repository [`IrrealV/supplymesh-webmcp`](https://github.com/IrrealV/supplymesh-webmcp); `main` still pointed to commit [`2f9a2196`](https://github.com/IrrealV/supplymesh-webmcp/tree/2f9a2196b938e9eb2f0bcdb87d7264c626e3a18c) at this check. The Devpost page alone was not used as proof of its internal implementation.

## Public-demo check and what to transfer

On 24 September, the deployed UI showed a full-height map with **15 synthetic vehicles**, status/risk filters, route and hazard layers, a legend, and a side inspection drawer with identity, route/ETA, reasons for attention and vehicle/cargo/driver tabs. Selection focuses a unit and exposes its context; the weather/traffic panel displayed **“Current data off”** until its optional live-data control is enabled. We did not invoke write tools, edit vehicles, or validate the optional external advisory feed. The README's offline/no-live-data claims describe the deterministic submission baseline; the presence of an optional live-data control in the deployed UI is **not** evidence that real-time data are reliable or part of CargoMesh.

For CargoMesh, transfer the **map-first layout, selection/highlight synchronization, explicit provenance and empty/error/unknown states**. Replace SupplyMesh's fleet-operation object with the selected `TransportPlanCandidate` and its `RoutePlan`; show shipper endpoints, eligible service/lane evidence, route source and capacity state in separate layers. This is a design reference for Juan's HAC-25 pilot and HAC-15 follow-up, not an extra requirement on Luis's HAC-24 intake prototype. Avoid the 3D truck, editable fleet, driver-rest workflow and incident recovery for the initial ROAD slice.

## What the reference actually implements

The current [README](https://github.com/IrrealV/supplymesh-webmcp/blob/2f9a2196b938e9eb2f0bcdb87d7264c626e3a18c/README.md) describes a React 19, Leaflet and optional Three.js **fleet-operations** console for a deterministic Spanish ROAD scenario. It reports 15 checked-in openrouteservice `driving-hgv` route geometries and no runtime routing dependency for that baseline. Fleet and incidents are synthetic; operational edits persist in browser storage, without backend, accounts or live tracking. Its current README documents 12 initial WebMCP tools and later workflow-specific tools; [`docs/architecture.md`](https://github.com/IrrealV/supplymesh-webmcp/blob/2f9a2196b938e9eb2f0bcdb87d7264c626e3a18c/docs/architecture.md) still describes the older four-tool Phase 1 boundary, so do not use that old count as the current product contract.

## Data required for a truthful V2 map emulation

An emulated **UI** is acceptable as a labelled V2 scenario; it must not fabricate service eligibility, a quoted offer or an authoritative ROAD route. Build the scenario under `supabase/scenarios/v2-*/` (seed + cleanup + verify), or keep a frontend-only contract fixture while the scenario is unapproved. Never insert synthetic catalog rows through a production migration or into the frozen WebMCP database.

| Data group | Minimum fields and source | Missing/negative treatment |
|---|---|---|
| Request endpoints | V2 request ID/organization, origin and destination names/country, optional facility IDs, coordinates with source/precision, pickup window. | If coordinates are absent, show textual endpoints and “location unresolved”; do not silently substitute V1 city anchors as exact addresses. |
| Candidate plan | `planId`, request ID, ordered `1..N` ROAD segments, carrier/service IDs **only when actually present in the V2 catalog**, required equipment/resources, proposed window and status. | `0` candidates is a valid result; a carrier's depot or map proximity does not create a plan. |
| Coverage and capacity | Pickup/delivery `ServiceArea`, directed `ServiceLane`, evidence/validity, supported load/mode, capacity calendar and reason codes. | Differentiate `eligible`, `ineligible` and `unknown`; no coverage inferred from a depot, no availability inferred from an empty agenda. The current remote ROAD tables are empty. |
| Road geometry | GeoJSON `LineString` `[lon,lat]` plus provider/profile, generated/verified time, source revision, endpoints/snap distance, geometry status `provider-verified` / `synthetic-demo` / `unavailable`. Distance and duration must have their own source, timestamp and units. | If no approved road geometry exists, show endpoints and an explicit “route unavailable” state. A straight line may be shown only as a labelled schematic, never as a drivable road, ETA or exact distance. |
| Route restrictions | Optional closure, height/weight limit, weather or border marker with geometry, source, validity, severity and affected segment. | Unknown legal/physical restriction stays `unknown` or `requires_review`. A map pin is not a verified permit, customs release, road closure or toll quote. |
| Commercial response | Attributed carrier offer ID, amount/currency/expiry/component provenance **only after a real V2 offer exists**. | No offer is displayed as a confirmed price or booking. Estimated cost and quoted cost remain separate. |

For the first demo, prepare **two independent V2 cases**: (A) one ROAD request with a provider-verified or explicitly synthetic labelled corridor and a plan card whose coverage/capacity state is honest; (B) the QA no-candidate case (such as uncovered Piura or the unsupported reverse lane) showing endpoints, exclusion reason and **no fabricated route/offer**. The current QA `v2-road-baseline` proposal can supply domain cases once its PR is accepted; it is not yet a deployed remote catalog. A validated fixture should include checks for duplicate route IDs, GeoJSON shape, coordinate order/ranges, endpoint agreement, provider/revision, distance/ETA units and risk-to-route references. Add keyboard, mobile, empty/error, provider failure and human-interpretation checks to HAC-25/HAC-15/QA.

## Decision boundary for HAC-25 and HAC-15

- HAC-25 (Juan) compares Google Maps with Leaflet + an authorized tiles/routing provider, documenting cost/quota, LATAM ROAD coverage, geocoding/routing, attribution/license, key exposure, fallback and evidence. This document is a reference **input**, not the ADR itself.
- HAC-15 consumes the chosen map adapter and V2 plan/route contract. It may add candidate selection, provenance badge, risk layers and empty/unknown states; it must not infer serviceability from visual geometry.
- Leaflet is a rendering library, not a routing provider. SupplyMesh's fixed ORS Spain routes cannot satisfy CargoMesh's dynamic ROAD discovery. If standard OpenStreetMap tile servers are considered for a public deployment, follow the [OSMF tile policy](https://operations.osmfoundation.org/policies/tiles/) (visible attribution, valid referer/caching, no bulk prefetch); choose a suitable tile service for expected load. The current OSMF policy specifies `tile.openstreetmap.org` without the `{s}` subdomain pattern used in SupplyMesh's component, so do not copy that tile URL verbatim.
- Keep the V2 map on the **separate deployment** described in [the WebMCP freeze workflow](../delivery/WEBMCP_FREEZE_AND_V2_WORKFLOW.md). Neither a map preview nor source-code inspiration authorizes changing the judged V1 site.
